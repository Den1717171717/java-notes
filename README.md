Как работает Bean Definition?
Сканирование и создание Bean Definition:
Когда Spring сканирует классы с аннотациями (например, @Component, @Service, @Repository), он создает Bean Definition для каждого из этих классов. Это объект, который описывает как создать бин и какие зависимости ему передать.
Регистрация Bean Definition в контексте:
Эти Bean Definition добавляются в контейнер (например, AnnotationConfigApplicationContext или GenericWebApplicationContext), и Spring использует их для создания и управления объектами. Например, если у вас есть сервис UserService, Spring создает Bean Definition для этого класса и регистрирует его в контейнере.
Жизненный цикл бина:
Жизненный цикл бина управляется в соответствии с его объявленной конфигурацией. Например, если бин создан как синглтон (по умолчанию), то он создается один раз и используется при каждом запросе в приложении. Если бин имеет прототипный жизненный цикл, то Spring будет создавать новый экземпляр бина каждый раз, когда он требуется.
Инъекция зависимостей:
Когда Spring создает бин, он также разрешает все его зависимости. Например, если у вас есть сервис, который зависит от репозитория, Spring будет искать соответствующий бин репозитория и передаст его в сервис. Эта зависимость конфигурируется через конструкторы, поля или сеттеры с аннотациями @Autowired.


@Service
public class UserService {
    private final UserRepository userRepository;

    @Autowired
    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public void doSomething() {
        // logic
    }
}
Когда Spring сканирует классы, он обнаруживает аннотацию @Service и создает Bean Definition для этого класса.
Bean Definition будет содержать информацию о том, что нужно создать экземпляр класса UserService.
Он также будет знать, что для создания этого бина нужно инжектировать зависимость — бин UserRepository.
Этот Bean Definition добавляется в ApplicationContext для последующего использования.




Ты правильно понял часть про load balancer: он распределяет запросы между копиями приложения/сервиса.

Но главный минус монолита не в том, что “всё горит на одном сервере”. Главный минус в том, что ты не можешь масштабировать только один проблемный компонент.

Допустим, у тебя приложение:

A — авторизация
B — каталог товаров
C — оплата
D — генерация PDF
В монолите

Всё лежит внутри одного приложения:

Server 1:
[A + B + C + D]

Если сильно загружен только D, например генерация PDF, ты не можешь отдельно добавить только D.

Ты покупаешь второй сервер и запускаешь там весь монолит целиком:

Server 1: [A + B + C + D]
Server 2: [A + B + C + D]

Load balancer распределяет запросы:

User requests → Load Balancer → Server 1 / Server 2

Проблема: тебе нужен был только дополнительный D, но ты вынужден дублировать A, B, C тоже.

То есть ты тратишь ресурсы на копии компонентов, которые вообще не были перегружены.

В микросервисах

Ты разделяешь приложение:

Auth Service
Catalog Service
Payment Service
PDF Service

Если перегружен только PDF Service, ты добавляешь копии только его:

Server 1: Auth + Catalog + Payment
Server 2: PDF
Server 3: PDF
Server 4: PDF

И тогда нагрузка на генерацию PDF идёт только между PDF-сервисами:

PDF requests → Load Balancer → PDF 1 / PDF 2 / PDF 3

Вот в этом плюс: масштабируется только то, что реально загружено.

Главная разница

Монолит:

Хочешь масштабировать один компонент → масштабируешь всё приложение

Микросервисы:

Хочешь масштабировать один компонент → масштабируешь только этот сервис
Твой вопрос про “всё равно сервер будет загружен”

Да, сервер всё равно может быть загружен. Но разница в том, чем именно он загружен.

В монолите второй сервер несёт весь набор:

A + B + C + D

Даже если реально нужен только D.

В микросервисах ты можешь сделать так:

Server 1: A + B + C
Server 2: D
Server 3: D
Server 4: D

То есть ресурсы уходят туда, где реально проблема.

Но микросервисы не всегда лучше

У микросервисов есть свои минусы:

сложнее деплой
сложнее сеть
сложнее транзакции
сложнее дебаг
нужен Docker/Kubernetes/monitoring

Поэтому для маленького проекта монолит часто лучше.

Простая формула:

Монолит = проще разрабатывать, сложнее гибко масштабировать.

Микросервисы = сложнее разрабатывать, проще масштабировать отдельные части.



  Как работает под капотом:
                           
  Spring управляет пулом соединений с БД. У каждого соединения есть флаг autoCommit:
  - autoCommit=false — изменения копятся в буфере, попадают в БД только при COMMIT                                                                                                                                       
  - autoCommit=true — каждый SQL-запрос сразу попадает в БД                                                                                                                                                              
                                                                                                                                                                                                                         
  Когда открывается @Transactional — Spring берёт соединение из пула и ставит autoCommit=false.                                                                                                                          
                                                                                                                                                                                                                         
  Когда встречается NOT_SUPPORTED — Spring откладывает текущее соединение в сторону и берёт другое с autoCommit=true. После выполнения метода — возвращает исходное соединение обратно.                                  
                                                                                                                                                                                                                         
  ---                                                                                                                                                                                                                    
  Практический эффект:

  @Transactional                     ← транзакция открыта, autoCommit=false
    save(user)                       ← в буфер, ещё не в БД                                                                                                                                                              
                                                                                                                                                                                                                         
    @Transactional(NOT_SUPPORTED)    ← транзакция приостановлена                                                                                                                                                         
      save(log)                      ← autoCommit=true, сразу в БД навсегда                                                                                                                                              
      throw RuntimeException()                                                                                                                                                                                           
                  
    ← исключение вернулось, транзакция откатывается                                                                                                                                                                      
    save(user) отменяется            ← был в буфере, стёрся
    save(log) остаётся               ← уже в БД, откат его не достанет                                                                                                                                                   
                                                                                                                                                                                                                         
  ---                                                                                                                                                                                                                    
  Когда используется в реальном мире:                                                                                                                                                                                    
                                                                                                                                                                                                                         
  Когда нужно чтобы операция сохранилась даже при ошибке — например audit-лог, запись о попытке платежа, метрики. Они должны попасть в БД независимо от того, откатилась основная операция или нет.




    Отличие от NOT_SUPPORTED:                                                                                                                                                                                              
                                                                                                                                                                                                                         
  ┌────────────────────┬────────────────────┬─────────────────────────┐
  │                    │   NOT_SUPPORTED    │      REQUIRES_NEW       │
  ├────────────────────┼────────────────────┼─────────────────────────┤
  │ Внешняя транзакция │ приостанавливается │ приостанавливается      │
  ├────────────────────┼────────────────────┼─────────────────────────┤
  │ Новая транзакция   │ не создаётся       │ создаётся новая         │                                                                                                                                                  
  ├────────────────────┼────────────────────┼─────────────────────────┤                                                                                                                                                  
  │ autoCommit         │ true               │ false (своя транзакция) │                                                                                                                                                  
  └────────────────────┴────────────────────┴─────────────────────────┘                                                                                                                                                  
                  
  ---
  Как работает в твоём коде:
                                                                                                                                                                                                                         
  processTransaction()  ← @Transactional (TX-1 открывается, autoCommit=false)
  │                                                                                                                                                                                                                      
  ├── userRepository.save(user)     ← в буфер TX-1
  │                                                                                                                                                                                                                      
  ├── logTransaction()              ← REQUIRES_NEW
  │     TX-1 приостанавливается                                                                                                                                                                                          
  │     TX-2 открывается (новая, независимая)
  │     │                                                                                                                                                                                                                
  │     ├── save(log)               ← в буфер TX-2
  │     │                                                                                                                                                                                                                
  │     └── TX-2 COMMIT ✓           ← лог сохранён в БД навсегда
  │                                                                                                                                                                                                                      
  │     TX-1 возобновляется
  │                                                                                                                                                                                                                      
  └── throw RuntimeException()
        TX-1 ROLLBACK ✗             ← save(user) отменяется                                                                                                                                                              
                                                                                                                                                                                                                         
  Итог в БД:                                                                                                                                                                                                             
  - Баланс пользователя — не изменился (TX-1 откатилась)                                                                                                                                                                 
  - Запись в логе — сохранилась (TX-2 закоммитилась до исключения)                                                                                                                                                       
                  
  ---                                                                                                                                                                                                                    
  Практический эффект такой же как NOT_SUPPORTED — лог сохраняется даже при ошибке. Но механизм другой: там нет транзакции вообще, здесь — своя отдельная транзакция.
                                                                                                                                                                                                                         
  ---             
  Когда использовать REQUIRES_NEW вместо NOT_SUPPORTED:                                                                                                                                                                  
                                                       
  Когда внутри метода нужны несколько операций как одно целое — либо все сохранились, либо все откатились, но независимо от внешней транзакции.
                                                                                                                                                                                                                         
  // Например: сохранить и лог, и уведомление вместе
  @Transactional(REQUIRES_NEW)                                                                                                                                                                                           
  public void logAndNotify(...) {
      save(log);                                                                                                                                                                                                         
      save(notification); // если упадёт — откатится и log тоже
  }                                                                                                                                                                                                                      
  // Но внешняя транзакция этого не знает
                                                                                                                                                          


Thought for a couple of seconds

Да, ты имеешь в виду два основных способа инициализации Singleton:

1. Eager initialization — ранняя / статическая инициализация
2. Lazy initialization — ленивая / динамическая инициализация
1. Eager initialization — объект создаётся сразу
public class Singleton {

    private static final Singleton INSTANCE = new Singleton();

    private Singleton() {
    }

    public static Singleton getInstance() {
        return INSTANCE;
    }
}

Что происходит:

private static final Singleton INSTANCE = new Singleton();

Объект создаётся сразу при загрузке класса, даже если он пока не нужен.

На собеседовании:

Eager initialization — это когда объект Singleton создаётся заранее, при загрузке класса. Такой вариант простой и thread-safe, потому что JVM гарантирует безопасную инициализацию static-полей. Минус — объект создаётся даже если он ни разу не понадобится.

Плюсы:

+ просто
+ thread-safe
+ нет synchronized

Минус:

- объект создаётся заранее
2. Lazy initialization — объект создаётся только когда нужен
public class Singleton {

    private static Singleton instance;

    private Singleton() {
    }

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }

        return instance;
    }
}

Что происходит:

if (instance == null) {
    instance = new Singleton();
}

Объект создаётся только при первом вызове getInstance().

На собеседовании:

Lazy initialization — это когда объект Singleton создаётся не сразу, а только при первом обращении к нему через getInstance(). Плюс — мы не создаём объект, если он не нужен. Минус — простой вариант не является thread-safe.

Проблема:

if (instance == null)

Если два потока одновременно зайдут сюда, оба могут увидеть null и создать два объекта.

Lazy thread-safe через synchronized
public class Singleton {

    private static Singleton instance;

    private Singleton() {
    }

    public static synchronized Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }

        return instance;
    }
}

Теперь thread-safe, но есть минус:

каждый вызов getInstance() синхронизирован

Даже когда объект уже создан.

Лучший lazy-вариант: static inner class
public class Singleton {

    private Singleton() {
    }

    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}

Это очень хороший вариант для собеседования.

Почему?

Singleton класс загрузился → объект ещё не создан
getInstance() вызвали → загрузился Holder → создался INSTANCE

То есть объект создаётся лениво, но при этом thread-safe.

На собеседовании:

Один из лучших вариантов lazy initialization — initialization-on-demand holder idiom. Внутренний static-класс Holder загружается только при первом вызове getInstance(), поэтому объект создаётся лениво. При этом инициализация static-поля потокобезопасна благодаря механизму загрузки классов JVM.
